# Размещение и настройки

Node.js 24 (проверено 24.18.0), npm, постоянный Node-процесс (не serverless) и записываемый постоянный диск для SQLite. В браузере календарь работает и по HTTPS, и по обычному HTTP; для рабочего адреса нужен HTTPS. better-sqlite3 — нативная зависимость: выполнять npm ci на целевой платформе, не переносить node_modules с Windows на Linux.

```sh
npm ci
npm run build
```

Запускать из корня проекта: нужны dist/, public/, node_modules/, drizzle/ и конфигурация. Миграции находятся вне dist/.

Пакет better-sqlite3 13 поставляет готовые модули для поддерживаемых платформ. В lock-файле сохранён gypfile=false: без него npm ci может ошибочно запустить node-gyp вместо готового модуля. Сохранять эту метаинформацию при обновлении lock-файла. Для платформ без готового модуля нужны средства сборки (Python/C++); перенос node_modules между ОС не поддерживается.

## Обычный режим

Скопировать .env.example в .env, указать постоянный путь базы и при необходимости токен секретной ссылки, затем `npm start` (он сам читает .env; переменные можно передать и через менеджер процессов). Генерация токена:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
npm start
```

`npm start` запускает scripts/render-start.mjs: наполняет пустую базу снимком сообщества, обновляет его из Google, слушает HOST (по умолчанию 0.0.0.0) и PORT (4321) и печатает сводку запуска. Прямой запуск dist/server/entry.mjs базу не наполняет.

CALENDAR_EXPERIMENT=local и токен длиной от 32 символов включают временный адаптер. Вход: https://<адрес-приложения>/#<токен>. Фрагмент обменивается на HttpOnly-cookie. Это временный вход, а не Telegram-авторизация. Без адаптера административные маршруты закрыты.

CALENDAR_ALLOW_REMOTE=1 разрешает внешний домен для админки и API (иначе они отвечают только на localhost). CALENDAR_ADMIN_OPEN=1 открывает админку и её API без входа — временное решение до Telegram-авторизации; при CALENDAR_ADMIN_OPEN=0 вход только по секретной ссылке.

Пустая база при `npm start` получает миграции и снимок событий сообщества из config/community-calendar.json; уже инициализированная база не перезаписывается. Существующие данные переносятся через SQLite backup (npm run backup). Ручные типы и события создаются в админке.

## Переменные

- HOST, PORT — адрес/порт процесса.
- CALENDAR_DATABASE_PATH — база SQLite; при `npm start` по умолчанию data/calendar.sqlite (рабочую указывать на постоянном диске).
- CALENDAR_ADMIN_OPEN — 1 открывает админку без входа; по умолчанию закрыта.
- CALENDAR_ALLOW_REMOTE — 1 разрешает внешний домен для админки и API.
- CALENDAR_EXPERIMENT, CALENDAR_EXPERIMENT_TOKEN — временный вход по секретной ссылке.
- CALENDAR_SYNC_INTERVAL_MS — синхронизация, по умолчанию 60000.
- CALENDAR_SHARED_FEED_URL — закреплённый iCal сообщества: админка не может заменить его другим источником. render-start.mjs задаёт его из config/community-calendar.json.
- Устаревшие CALENDAR_PUBLIC_DEMO=1 и CALENDAR_DEMO_REMOTE=1 по-прежнему понимаются как CALENDAR_ADMIN_OPEN=1 и CALENDAR_ALLOW_REMOTE=1, чтобы ранее настроенный хост не сломался. CALENDAR_SHARED_CALENDAR, CALENDAR_SHARED_DATABASE_PATH и CALENDAR_PUBLIC_DEMO_DIRECTORY больше не используются.
- CALENDAR_BACKUP_DIR, CALENDAR_BACKUPS_KEEP — каталог/число копий, по умолчанию backups и 14.
- GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET — старый OAuth; для iCal не нужны.

## Данные

SQLite хранить на постоянном диске. Seed-скрипты не запускать поверх произвольной рабочей базы. seed-shared-calendar.mjs при первой инициализации очищает события/типы и загружает первоначальный снимок; это не миграция рабочих данных.

```sh
npm run backup
```

Backup читает CALENDAR_DATABASE_PATH. Shell или менеджер процессов должен загрузить переменные: backup сам не читает .env. Для резервного копирования используется online backup SQLite.

Перед заменой базы остановить приложение, использовать проверенную копию и проверить запуск. Один файл, скопированный из работающей WAL-базы, не гарантирует полный снимок.

CALENDAR_BACKUPS_KEEP должен быть целым числом от 1. Неверное значение останавливает backup до записи и удаления копий. Отсутствующая исходная база также вызывает отказ, а не создание пустой базы. Имена копий уникальны; копии следует регулярно переносить на отдельное хранилище и проверять восстановление. Автоматического расписания backup в приложении нет — его настраивает команда размещения.

## Действующий стенд

render.yaml описывает бесплатный Render-сервис и scripts/render-start.mjs. Launcher читает .env, при первом запуске базы загружает снимок из config/community-calendar.json (повторный запуск данные не перезаписывает), закрепляет этот iCal как источник и сразу обновляет его из Google; дальше работает фоновая синхронизация. База — CALENDAR_DATABASE_PATH, по умолчанию data/calendar.sqlite.

Диск бесплатного стенда эфемерен: внутренние настройки не гарантированы после redeploy/restart. Для постоянной работы нужны постоянный диск, backup и рабочая авторизация. Уборка репозитория настройки стенда не меняет.

Для рабочего запуска указать CALENDAR_DATABASE_PATH на постоянном диске; render-start.mjs подходит и для него (снимок загружается только в пустую базу). Чтобы закрыть админку, установить CALENDAR_ADMIN_OPEN=0 и удалить устаревший CALENDAR_PUBLIC_DEMO, если он задан в настройках хоста: вход останется по секретной ссылке. Отключить временный CALENDAR_EXPERIMENT после подключения доверенной серверной идентификации Telegram/сессии; без новой интеграции это закроет админку полностью. Не переносить в рабочую систему параметр participant как доказательство личности.

## Основной сайт

Будущий внешний адрес — https://ersdsgn.club/cal, внутренний маршрут — /calendar. Схему подключения определяет команда сайта. Ресурсы используют корневые /_astro/, /assets/, /fonts/ и /api/...; при конфликте с сайтом нужна адаптация. Глобальная замена маршрутов админки не требуется.

Прокси передаёт исходные Host/X-Forwarded-Host и X-Forwarded-Proto. Запросы записи проверяют Origin. Календарь и админка должны получать общие актуальные данные. Не открывать все /api/ ради публичного календаря; список — INTEGRATION.md.

После размещения: прямое открытие/reload, ресурсы, API, совпадение данных с админкой, права, обложки, мобильная карточка, ссылки и backup. Будущий адрес в рамках уборки не подключается.
